## 3. vllm

在之前的实现里，系统会为每个请求预留一块**连续的、巨大的**显存空间来存放这个动态增长的 KV Cache，这样在 static batch 里，系统会根据一个预设的**最大序列长度 (max_length)**，为这**整个批次**一次性地在显存中申请一块**巨大且连续**的空间，用来存放所有请求的 KV Cache，他们在实际情况中也被一起处理、一起释放，不会遇到问题。

但换到continuous batching之后，原先的内存块被拆碎了，不同的内存大小要求也不一样，就会出现，一个短请求结束后，它释放的连续空间可能太小，无法容纳一个新的长请求，从而造成空间闲置。

   *   vLLM 借鉴了操作系统管理内存的“分页”思想。
   *   它不再分配连续的大块内存，而是把整个 KV Cache 的显存空间切分成N个**固定大小的小块（Block）**。
   *   每个请求的 KV Cache 不再是连续存放的，而是由**一系列离散的 Block** 组成。
   *   系统会为每个请求维护一个 **“块表 (Block Table)”**，这个表记录了该请求的“逻辑”顺序和这些 Block 在显存中的“物理”位置的对应关系。

这样，当一个请求需要生成新 Token 时，只需分配一个新的 Block，并更新块表即可。当一个请求结束时，只需将其所有 Block 标记为“空闲”即可回收。

具体操作步骤：

基于 PagedAttention 这个强大的地基，三个核心组件开始高效协作：

1. KV Cache Manager (内存管理员)
*   **职责：** 专门管理所有的物理 Block。
*   **功能：**
    *   **分配 (Allocate)：** 当调度器决定要运行一个新请求时，它会向 Manager 申请 N 个 Block 用于 Prefill。当一个请求要生成新 Token 时，它会申请 1 个 Block。
    *   **释放 (Free)：** 当调度器发现一个请求结束了，它会通知 Manager 释放该请求占用的所有 Block。
    *   **维护块表 (Block Table)：** 为每个请求创建和更新它们的块表。

2. Scheduler (调度器 / 大脑)
*   **职责：** 决定**下一个迭代周期（时间步）要运行哪些请求**，以及它们是做 Prefill 还是 Decode。
*   **工作流程（一个心跳周期）：**
    1.  **检查结束的请求：** 扫描上一轮运行的请求，看谁生成了 END 标记。如果有，就通知 KV Cache Manager 释放资源。
    2.  **评估资源：** 问 KV Cache Manager：“现在还剩多少个空闲的 Block？”
    3.  **决策优先级：**
        *   **优先接纳新请求 (Prefill)：** 它会查看等待队列（Request Queue），并估算新请求做 Prefill 需要多少 Block。如果资源足够，就把它加到“待运行”列表里。优先处理 Prefill 是因为这能尽快让更多请求进入 Decode 阶段，从而把整个批次做得更大。
        *   **处理现有请求 (Decode)：** 把所有已经在运行中、需要生成下一个 Token 的请求也加入“待运行”列表。
    4.  **形成混合批次：** 将所有被选中的 Prefill 和 Decode 任务打包成一个**混合批次（Mixed Batch）**。
    5.  **下达指令：** 把这个混合批次交给执行器去运行。

3. Model Executor (执行器 / 肌肉)
*   **职责：** 真正与 GPU 打交道，执行模型运算。
*   **功能：**
    *   接收调度器发来的混合批次。
    *   根据每个请求的块表（由 KV Cache Manager 提供），准确地从离散的物理 Block 中读取正确的 KV Cache。
    *   调用底层的 CUDA Kernel 进行矩阵运算。
    *   将新生成的 KV Cache 写回到为它们新分配的 Block 中。
    *   返回生成的 Token。


1.  **请求进入队列：** 用户请求 `S5` 到达，进入等待队列。
2.  **调度器决策：** 在下一个调度周期，调度器发现有空闲 Block，决定接纳 `S5`。
3.  **内存分配 (Prefill)：** 调度器向 KV Cache Manager 为 `S5` 申请 Prefill 所需的 Block。Manager 分配成功，并创建 `S5` 的块表。
4.  **执行混合批次：** 调度器将 `S5` 的 Prefill 任务，和正在运行的 `S1, S2, S4` 的 Decode 任务，打包成一个混合批次，交给执行器。
5.  **进入解码循环 (Decode)：** 在后续的周期中，`S5` 变成了 Decode 任务。调度器每次都会为它申请 1 个新的 Block，并把它和其他请求的 Decode 任务一起打包执行。
6.  **请求结束并释放：** 假设 `S1` 结束了，调度器会通知 Manager 释放 `S1` 占用的所有 Block。这些 Block 立刻变成空闲状态，可以在下一个周期被新的请求（如 S6）使用。

## 4. DistServe

根据之前的观察，LLM分成prefill（指标：TTFT）和decoding（指标：TPOT）这两个阶段。之前的continuous batching会把不同用户的prefill和decode拼在一起在GPU上跑。

1. Decode 每一步本来很快，但如果和别人长长的 Prefill 拼在一起，Decode 就得干等着 Prefill 算完。导致 TPOT 暴增；反之，GPU 为了兼顾 Decode，也会拖慢 TTFT。

2. **Chunked Prefill（分块预填充）治标不治本**：有人说，把长 Prefill 切成小块不就行了？（DeepSpeed-MII的做法）。但论文指出，切块会引入大量的额外显存访问开销（KV Cache 需要反复加载），总开销变成了  $O(N^2)$，反而更慢。
    
3. **资源耦合（Resource Coupling）**：Prefill 需要计算力，适合用张量并行（Intra-op parallelism）来降低延迟；Decode 需要高并发，适合用流水线并行（Inter-op parallelism）或多卡副本来提升吞吐。把它们绑在一张卡上，只能妥协，导致**过度配置（Over-provisioning）**。

因此DistServe希望把Prefill和Decode放到不同的GPU上, <font color="#ff0000">然后采用不同的并行策略</font>

我希望能够在满足TTFT和TPOT要求的时候，**最大化 Per-GPU Goodput（单卡有效吞吐量）**。

### Prefill

Prefill 的目标是：用最少的资源满足 TTFT 要求。

*   **Batching 策略**：因为 Prefill 是计算密集（Compute-bound）的，当输入的 Token 数量超过某个阈值 $L_m$ 时，GPU 算力就吃满了(计算的算力上限——同时处理 $L_m$ 的计算任务)。这时候再增加 Batch Size 只会排队，没啥好处。所以 Prefill 的 Batch Size 通常很小。
*   **并行策略（排队论登场）**：
    作者用 $M/D/1$ 队列模型来分析 TTFT。假设单个请求执行时间恒定为 $D$，到达率是 $R$。
    那么平均首字延迟为：
    $$Avg\_TTFT = D + \frac{R D^2}{2(1 - RD)}$$
    *(第一项是执行时间，第二项是排队等待时间)*

    如果使用流水线并行（Inter-op），执行时间几乎不变（仍约为 $D$），但可以承受更高的 $R$。
    如果使用张量并行（Intra-op），虽然通信有开销（引入加速折扣因子 $K, 1 < K < 2$），但执行时间变成了 $\frac{D}{K}$：
    $$Avg\_TTFT_{intra} = \frac{D}{K} + \frac{R D^2}{2K(K - RD)}$$
    **结论：** 当请求率较低或 SLO 极度严格时，选**张量并行**（降执行时间）；当请求率高、排队严重时，选**流水线并行**（扩充吞吐）。

### Decode

decode主要采用：为了保证生成每个 Token 够快（满足 TPOT），需要用张量并行来降延迟；一旦延迟达标了，剩下的资源全拿去做流水线并行或多副本来横向扩展。

#### 1. 核心矛盾：显存带宽瓶颈

在推理时，Decode 阶段每生成一个 Token 都要读一遍巨大的模型权重。

- **痛点**：由于 GPU 的算力远超显存读取速度，如果 Batch Size 很小，GPU 大部分时间都在“等数据”，造成极大的算力浪费。
    
- **解决方案**：为了填满 GPU 的胃口，必须增加 **Batch Size**（并发数）。Batch 越大，平均到每个 Token 上的权重读取开销就越小，性价比越高。
    
#### 2. 解耦：多对一的“投喂”模式

在传统的混合模式下，Prefill（输入长、计算密集）和 Decode（输出慢、显存密集）互相抢资源。

- **以前的问题**：Prefill 很快就结束了，但 Decode 慢腾腾地占着位置，导致 Batch Size 很难攒大。
- **现在的解耦**：我们可以让 5 台机器专门负责 Prefill，把处理好的请求源源不断地塞给 1 台专门负责 Decode 的机器。
- **结果**：Decode 实例就像一个高效的流水线末端，瞬间攒够 128 甚至 256 个请求一起跑，彻底榨干 GPU 的带宽。

#### 3. TPOT 与并行策略的取舍

**TPOT (Time Per Output Token)** 是衡量用户“丝滑感”的核心指标（即生成两个字之间的时间间隔）。

- **张量并行 (Tensor Parallelism, TP)**：
    - **目的**：把一个模型的计算任务横向劈开，让多张显卡一起算一个请求。
    - **效果**：单次计算变快，**降低延迟**。只要延迟降到了用户感知的临界点（比如 50ms/token），就说明 TP 给够了。
- **流水线并行 (Pipeline Parallelism, PP) / 多副本**：
    - **目的**：在延迟达标的前提下，增加系统的总吞吐量。
    - **逻辑**：如果 TP 已经让速度够快了，再加 TP 边际效应会递减（通信开销大）。这时候，多弄几个副本或者分层跑，能让系统同时处理更多的用户请求。

#### 总结

这段话的精髓在于：**术业有专攻**。

把 Decode 独立出来后，通过**大 Batch** 解决效率问题，通过 **TP** 解决速度问题，最后通过 **PP 或副本** 解决规模问题，从而用最少的服务器资源满足最严苛的实时生成要求。

想深入了解一下在这种架构下，**KV Cache（键值缓存）** 是如何在 Prefill 和 Decode 实例之间传输的吗？这是目前工程实现上的最大挑战。

### 通信开销

把它们分开后，Prefill 算完的中间结果（巨大的 KV Cache）需要通过网络传给 Decode 机器。如果一个请求 512 token，KV Cache 大概 1.13GB，10 QPS 的话就需要 90Gbps 的带宽。
**结论**：在有 InfiniBand（800 Gbps）的高端集群，这都不是事。但如果在只有普通网线的跨节点集群，就必须把同一组的 Prefill 和 Decode 放在同一个物理机（Node）内，用 NVLINK（600 GB/s）传。

> 实验证明，因为算法巧妙地把同 Stage 放在了同一个物理机内，**KV Cache 的传输时间占整个生命周期的比例不到 0.1%！** 超过 95% 的请求传输延迟低于 30 毫秒。完全是可以忽略不计的。

部署方法：

> [!note]+ 调度算法
> ## 🧠 3. 核心算法：自动寻找最佳配置 (Method)
> 
> 理解了原理，怎么在几十张卡上部署呢？DistServe 写了一个调度器，给它模型信息、用户流量预估，它能自动吐出最优的集群配置。针对不同的硬件网络，设计了两个算法：
> 
> ### 3.1 算法1：高节点亲和力放置 (High Node-Affinity Cluster)
> 适用于高端土豪集群（跨节点网速极快，KV Cache 随便传）。
> *   **逻辑**：把 Prefill 和 Decode 完全独立看待。
> *   **做法**：
>     1. 穷举 Prefill 所有可能的并行组合（流水线、张量并行）。
>     2. 用一个精确的 **Simulator（模拟器）** 跑一遍，看看满足 TTFT SLO 下，单卡最高 QPS 是多少，选最好的配置。
>     3. 同理，穷举 Decode 的配置，用模拟器跑，选满足 TPOT SLO 下单卡 QPS 最高的。
>     4. 最后根据总流量，按比例复制 Prefill 和 Decode 实例（比如 3个 Prefill 喂 2个 Decode）。
> 
> ### 3.2 算法2：低节点亲和力放置 (Low Node-Affinity Cluster)
> 适用于普通集群（跨节点网速慢，只能靠单机内的 NVLINK 传 KV Cache）。
> *   **逻辑**：必须强行把负责模型某一层（Stage）的 Prefill 和 Decode 实例绑在同一个物理机（Node）内。
> *   **做法**：直接穷举单台机器内部，GPU 如何划分给 Prefill 和 Decode 的组合，用模拟器跑出局部最优解，然后整机复制。
> 
> ### 3.3 在线调度优化 (Online Scheduling)
> 跑起来之后，怎么让流水线不卡顿？
> 1.  **减少流水线气泡**：用户的 Prompt 长短不一，长短混跑会导致有的卡闲着。DistServe 根据饱和长度 $L_m$ 把请求打包，尽量让每个 Batch 耗时差不多。
> 2.  **对抗突发流量**：采用 **Pull（拉取）** 机制。Prefill 算完后，KV Cache 暂存在自己卡上；Decode 那边如果消化不过来，不去强塞，等 Decode 空闲了主动去 Prefill 那里拉取。
> 


> [!note]- 延迟数学模型
> 
> 大模型的推理时间到底是怎么算出来的？作者在附录给出了严密的 FLOPs（浮点运算次数）和内存读写量的公式：
> 
> ### 6.1 Prefill 阶段的算力模型 (Compute-bound)
> 对于常规的线性层（QKV, FFN等），它的运算强度（Arithmetic Intensity）是 $O(t)$，其中 $t$ 是输入的 token 总数。如果 $t$ 很大，这绝对是**算力瓶颈**。
> 总计算时间大约由 FLOPs 决定：
> $$T_1 = C_1 \cdot (4th^2 + 2thm)$$
> *(h是hidden size, m是FFN size, $C_1$是常数)*
> 
> 而由于加入了 FlashAttention 优化，Attention 部分反而变成了内存瓶颈，其时间模型为：
> $$T_2 = C_2 \cdot \frac{3ht_2}{b}$$
> *(这里 $t_2$ 是输入长度的平方和)*
> **总之，Prefill 的时间主要受算力（GPU 频率）影响最大。**
> 
> ### 6.2 Decoding 阶段的算力模型 (Memory-bound)
> Decode 时每次只处理 1 个 token。虽然要做很多运算，但为了做这些运算，必须把巨大的权重从显存搬进来。
> 对于线性层，需要读写的内存总量是：$8Bh + 4h^2 + 2hm + 2Bm$ （$B$ 是 Batch Size）。
> 它的执行时间公式为：
> $$T_{Decoding} = C_4 \cdot (4h^2 + 2hm) + C_5 \cdot 3ht$$
> 在这个公式里，占大头的 $4h^2 + 2hm$ 跟 Batch Size ($B$) 竟然没有直接关系！（实际上是因为 $h$ 和 $m$ 远大于 $B$）。
> **这意味着：在 Decode 阶段，只要 Batch Size 还没大到把显存塞满，你增大 Batch Size，耗时几乎不会怎么增加！这也是为什么 Decode 必须用大 Batch 才能提高效率的原因。**


> [!note]+ 和Programming的联系
> 
> 1.  **关于 Task 3 (Prefill vs Decode Power)**：
>     根据这篇论文的附录分析，Prefill 疯狂做大矩阵乘法（Compute-bound），此时 GPU 计算单元拉满，**你会观察到 Prefill 阶段的 Power (功耗) 显著高于 Decode 阶段**。Decode 阶段由于都在等显存搬运数据（Memory-bound），计算单元常常在“摸鱼”，所以功耗相对较低，但消耗的整体时间长。
> 2.  **关于 Task 4a (GPU 频率的影响)**：
>     因为 Prefill 是算力瓶颈，**降低 GPU 频率（降频）会导致 Prefill 的处理速度（吞吐）成比例下降**。
>     但对于 Decode 阶段，因为它的瓶颈在显存带宽（Memory clock），降低计算频率可能**对 Decode 的吞吐量影响不大**（它本来就不缺算力），反而能大幅降低没必要的功耗浪费。这可能就是一个节省 Energy/token 的 "Sweet Spot"（甜蜜点）！
> 3.  **关于 Task 4b (Batch Size 的影响)**：
>     根据附录的 $T_{Decoding}$ 公式，增大 Batch Size，模型权重（Weights）的复用率提高（一次显存读取，给多个 request 用）。你会观察到，随着 Batch Size 增大，**吞吐量 (tokens/sec) 会显著提升，而每生成一个 token 的能耗 (J/token) 会大幅下降**，直到遇到显存墙或者达到了算力瓶颈阈值。这正好印证了文中为什么建议将多个 Prefill 聚合成一个巨大的 Decode Batch 的初衷！

## 5. SplitWise

decode和prefill作为不同阶段的计算特性，决定了它们天生就该跑在不同型号、不同功耗的 GPU 上

> [!question] why
> 算力（TFLOPS）：H100 是 A100 的 3.43倍！简直是暴力猛兽。
> 显存带宽（HBM Bandwidth）：H100 仅仅是 A100 的 1.64倍。
> 功耗（Power）：H100 是 A100 的 1.75倍。
> 价格（Cost）：H100 是 A100 的 2.16倍。

1. **Prefill（预填充）阶段**：**计算密集型 (Compute-bound)**。它极度渴望算力，H100 的 3.43 倍算力能让它如虎添翼，TTFT（首字延迟）大幅降低。
    
2. **Decode（解码）阶段**：**访存密集型 (Memory-bound)**。它的瓶颈在显存带宽，算力常年闲置。你给它一个算力是 3.43 倍的 H100，它根本用不上，提升微乎其微，纯属 **“杀鸡用牛刀”** ，白白浪费了电和钱。


为了证明上面的论断，作者进行了一系列详尽的底层测试，得出了一连串的 Insights (洞察)，这些洞察是整篇论文的基石。

- **Insight I & II：负载天差地别，传统批处理效率低下。**  
    这部分和 DistServe 结论一致，实际生产环境中（如代码补全和对话），负载变化剧烈，传统批处理（Mixed Batching）大部分时间都在处理小批量的 Decode 任务，效率极低。
    
- **Insight III & IV：时间都去哪了？Decode 阶段是耗时大户。**  
    实验发现，即使是输入很长的 Prefill，其耗时也远小于后续一个一个蹦字的 Decode 阶段的总耗时。同时，**Decode 阶段的吞吐量随着 Batch Size 增大而持续飙升，而 Prefill 的 Batch Size 超过一个很小的阈值后，性能就会急剧下降。** 这再次从实验上论证了“拆分”的必要性。
    
- **Insight V & VI：功耗的秘密！这部分对你的 Task 至关重要！**
    

![|425](Pasted%20image%2020260309220739.png)
    
- **功耗与负载**：Prefill 阶段的功耗随着 Batch Size 增大而**显著增加**，因为它在压榨算力。而 Decode 阶段的功耗几乎是**一条平线**，无论 Batch Size 多大，功耗都差不多，因为它总是在等访存。
	
- **功耗限制 (Power Capping)**：作者丧心病狂地把 H100 的功耗从 700W 一路砍到 350W（腰斩！）。结果发现：
	- Prefill 的延迟**急剧恶化**。
	- Decode 的延迟**几乎没有变化**！  
		**这说明：Decode 阶段在满功率运行时，大量的能量被浪费掉了，我们完全可以给它降频降压运行，性能几乎无损！**
            
- **Insight VII：异构硬件的性能对比。**
    
![|450](Pasted%20image%2020260309220831.png)

- 对于 Prefill (看 TTFT)，H100 性能是 A100 的近两倍。
	
- 对于 Decode (看 TBT/TPOT)，H100 只比 A100 快了 30% 左右。  
	**结论：** 考虑到价格和功耗，用更便宜、更省电的 A100 来跑 Decode 阶段，其**性价比（Perf/W 和 Perf/$）远高于 H100！**

因此，Splitwise的设计：它把集群分成了三个动态的**资源池**：

1. **Prompt Pool (Prefill 池)**：专门放运行 Prefill 的机器。根据前面的分析，这里最好放 H100 这种算力猛兽。
2. **Token Pool (Decode 池)**：专门放运行 Decode 的机器。这里可以放 A100 这种性价比之王，甚至可以给它们**限制功耗**运行。
3. **Mixed Pool (混合池)**：这是一个灵活的“摇摆池”。当某个池子压力过大时，可以从另一个池子临时借调机器到混合池里，用传统方式（不拆分）运行，以应对突发流量，防止系统崩溃。

> [!note]- 通信调度
> 好的，这个问题非常棒，直接切入了“解耦”方案最核心的工程挑战——**如何处理因拆分而产生的通信开销**。DistServe 和 Splitwise 在这个问题上采取了不同层次的优化策略，理解它们的差异对于评估这类系统的可行性至关重要。
> 
> 我们来详细拆解一下这两种 KV Cache 的传输优化方案。
> 
> ---
> 
> ### 📚 1. 基础知识：KV Cache 是如何生成的？
> 
> 首先，我们要明白 KV Cache 不是一个一次性生成的“铁块”，而是在 Prefill 阶段**逐层（Layer-by-Layer）**生成的。
> 
> 一个 Transformer 模型由很多个相同的 Block（或 Layer）堆叠而成，比如 Llama-70B 有 80 层。当 Prefill 计算时，数据流是这样的：
> *   **输入 Tokens** -> 计算 **Layer 1** -> 生成 **Layer 1 的 KV Cache**
> *   **Layer 1 的输出** -> 计算 **Layer 2** -> 生成 **Layer 2 的 KV Cache**
> *   ...
> *   **Layer 79 的输出** -> 计算 **Layer 80** -> 生成 **Layer 80 的 KV Cache** -> **生成第一个输出 Token**
> 
> 所以，整个 Prefill 过程结束时，我们得到的是 80 份独立的、属于不同层的 KV Cache。这为“边计算边传输”提供了物理可能性。
> 
> ---
> 
> ### 🐢 2. DistServe 的传输策略：Pull 机制，简洁但有延迟
> 
> DistServe 的论文主要强调了系统架构和调度算法，对于 KV Cache 的传输细节，它提出的核心是 **"Pull" (拉取) 机制**。它没有深入到像 Splitwise 那样细粒度的传输优化，其默认的传输方式更接近于一种**“批处理”**或**“宏观”**的传输。
> 
> #### DistServe 的传输流程：
> 
> 1.  **计算完成**：Prefill 实例（机器A）**完整地运行完所有层**，生成了全部的 KV Cache (从 Layer 1 到 Layer 80) 以及第一个输出 Token。
> 2.  **数据暂存**：这些完整的 KV Cache 会被**暂存在 Prefill 实例 A 的 GPU 显存中**。这就像一个“发货区”，货物已经打包好了，等待提货。
> 3.  **Decode 就绪**：当 Decode 实例（机器B）有空闲资源时（比如处理完了上一批请求），它会向中央调度器发出信号：“我准备好了，可以接新活了！”
> 4.  **发起拉取**：调度器指示 Decode 实例 B，去 Prefill 实例 A 的“发货区”**拉取（Pull）**那个刚刚准备好的、完整的 KV Cache。
> 5.  **开始 Decode**：Decode 实例 B 接收完**所有** KV Cache 后，才开始进行后续的 Token 生成。
> 
> #### 优缺点分析：
> 
> *   **优点**：
>     *   **架构简单、解耦彻底**：Prefill 和 Decode 实例之间没有紧密的实时依赖。Prefill 只管生产，Decode 只管消费。这种异步机制可以很好地**对抗突发流量**，防止 Decode 实例被冲垮。
>     *   **鲁棒性好**：逻辑清晰，易于实现和管理。
> *   **缺点**：
>     *   **存在明显的串行延迟**：传输必须在**整个 Prefill 计算完全结束之后**才能开始。这意味着，**传输时间 (Transmission Time) 是一个纯粹的、无法被隐藏的额外开销**。
>     *   **对网络带宽要求更高**：因为它需要在短时间内传输一个巨大的、完整的数据块。
> 
> **总结一下 DistServe**：它的重点在于系统层面的流量控制和资源匹配，传输本身被视为一个原子性的、在 Prefill 和 Decode 两个阶段**之间 (In-between)** 发生的操作。
> 
> ---
> 
> ### 🚀 3. Splitwise 的传输策略：Layer-wise 异步传输，极致的延迟隐藏
> 
> Splitwise 作为一篇体系结构领域的论文，对延迟的优化有着极致的追求。它认为 DistServe 那样的串行延迟是不可接受的，于是提出了 **Layer-wise Asynchronous Transfer（逐层异步传输）**。
> 
> #### Splitwise 的传输流程（以 Llama-70B 为例）：
> 
> ![](Pasted%20image%2020260309221032.png)
> 
> 1.  **Layer 1 计算完成**：Prefill 实例 A 的 GPU 计算完 **Layer 1**，生成了 Layer 1 的 KV Cache。
> 2.  **立刻启动传输**：就在 Prefill 实例 A 的 GPU **开始计算 Layer 2 的同时**，CPU 会立刻发起一个**异步的、非阻塞的**网络传输指令，把刚刚生成的 **Layer 1 的 KV Cache** 发送给 Decode 实例 B。
> 3.  **计算与通信并行**：
>     *   Prefill 实例 A 的 GPU 在算 **Layer 3**。
>     *   与此同时，网络硬件正在传输 **Layer 2 的 KV Cache**。
>     *   与此同时，Decode 实例 B 可能已经在接收 **Layer 1 的 KV Cache**。
> 4.  **流水线式进行**：这个“计算一层、传输一层”的过程像流水线一样持续进行。
> 5.  **无缝衔接**：当 Prefill 实例 A 的 GPU 算完最后一层（Layer 80），并生成第一个输出 Token 时，**绝大部分（甚至全部）的 KV Cache 已经传输完毕**，并静静地躺在 Decode 实例 B 的显存里了。
> 6.  **立即开始 Decode**：Decode 实例 B 几乎不需要任何等待，可以立即开始它的第一个 Decode 步骤。
> 
> #### 优缺点分析：
> 
> *   **优点**：
>     *   **极致的延迟隐藏**：它把原本纯粹的额外开销（传输时间）**几乎完全隐藏在了 Prefill 的计算时间之内**。从外部看，传输仿佛是“免费”的。实验表明，可见的（未被隐藏的）传输延迟被压缩到了**个位数毫秒**。
>     *   **平滑网络负载**：把一次性的巨大数据传输，分解成了 80 次小的数据包传输，降低了对网络峰值带宽的冲击。
> *   **缺点**：
>     *   **实现复杂**：需要非常细粒度的软硬件协同。GPU 正在计算，CPU 需要精准地同步、触发 DMA (直接内存访问) 和网络传输，对驱动和底层通信库（如论文中提到的 MSCCL++）要求很高。
>     *   **存在微小干扰**：频繁的传输启动可能会对 CPU 造成一定的干扰，对于**极短的 Prefill 请求**（比如只有几十个 Token），这种细粒度同步的开销可能反而会拖慢一点点 TTFT。因此，Splitwise 还提到会根据 Prompt 长度动态选择策略：**长的用逐层传输，短的用整体传输**。
> 
> ---
> 
> ### 🎯 总结对比
> 
> | 特性 | DistServe (Pull 机制) | Splitwise (Layer-wise 异步传输) |
> | :--- | :--- | :--- |
> | **核心思想** | 流量控制，宏观解耦 | 极致延迟隐藏，微观并行 |
> | **传输时机** | Prefill **计算完全结束后**，作为一个整体传输 | Prefill **计算过程中**，与计算并行、逐层传输 |
> | **延迟表现** | 传输时间是**纯粹的额外开销**，无法隐藏 | 传输时间**绝大部分被隐藏**在计算时间内 |
> | **实现复杂度**| 相对简单，逻辑清晰 | 非常复杂，需要软硬件深度协同 |
> | **适用场景** | 普适性强，强调系统稳定性和弹性 | 追求极致低延迟，对工程实现要求高 |
> | **好比** | **仓库发货**：等所有货都打包好，再叫卡车一次性拉走。 | **传送带**：工厂里一个零件加工好，立刻被传送到下一个工位。|
> 
> 通过这个对比，你可以看到 Splitwise 在工程实现上比 DistServe 更进一步，更深入地挖掘了硬件的并行潜力，以换取那至关重要的几十毫秒延迟优化。这也体现了计算机系统（OSDI/SOSP）和计算机体系结构（ISCA/MICRO）两个领域会议的不同侧重点。

总体调配：Autoscale

Autoscaling 是云计算中的经典概念，指系统根据实时的负载情况（流量大小），自动增加或减少 GPU 节点的数量 。

在BiScale中，Auto-scale 被视为一种**“粗粒度”**的节能手段。

- **操作逻辑**：当请求多时，多开几台服务器；请求少时，关掉一些显卡以节省电费 。
- **局限性（本文痛点）**：
    - **响应太慢**：重新配置（Reconfiguration）非常耗时。例如，加载一个几十 GB 的大模型权重到 GPU 显存里需要分钟级的时间 。
    - **无法处理细微波动**：由于加载慢，它无法跟上毫秒/秒级的流量瞬时起伏 。
    - **过度冗余（Over-provisioning）**：为了防止流量突然增加导致卡顿，服务商不得不按照“峰值负载”预留多余的显卡，导致非高峰期产生大量能耗浪费 。

更多采用DVFS：Dynamic Voltage and Frequency Scaling

**DVFS (Dynamic Voltage and Frequency Scaling)** 是现代 GPU 支持的一项硬件功能。
- **功能**：允许系统在几十毫秒的微观时间尺度内，动态调整 GPU 核心（SM）的**时钟频率**和对应的**电压状态**。
- **现状**：它在 LLM **训练**阶段已经非常成熟，能降低约 **30%** 的能耗且几乎不影响性能。

## 6. DynamoLLM

1. **异构性 (Heterogeneity):**
    - **请求不同**：有的请求输入很长（比如总结一篇长文），有的输出很长（比如写一个故事）。
    - **模型不同**：不同的 LLM 模型（如 Llama-7B, Llama-70B）计算特性千差万别。
    - **SLO 不同**：聊天机器人对延迟很敏感，而离线分析任务则可以容忍更高延迟。
        
2. **波动性 (Fluctuations):**
    - 用户的访问量有明显的高低峰（比如白天工作时间访问多，半夜就少）。

**挑战是什么？**
既然有机会，为什么大家之前没做呢？因为这太复杂了。系统配置的“旋钮”太多了：
*   用多少台服务器？（实例数量伸缩）
*   每台服务器里，一个模型用几张 GPU 卡？（模型并行度）
*   GPU 的运行频率是高还是低？（GPU 频率缩放）

这些“旋钮”组合起来，形成了一个巨大的“搜索空间”。在动态变化的工作负载下，想实时找到那个既满足性能 SLO 又最省电的“最优配置点”，简直难于上青天。

**DynamoLLM 的诞生：**
为了解决这个挑战，作者提出了 **DynamoLLM**，这是业界第一个专门为 LLM 推理环境设计的 **能量管理框架**。它的核心思想就是：**自动化、动态地调整推理集群的配置，以在满足 SLO 的前提下，实现能耗最低。**

最终效果惊人：在服务层面，DynamoLLM 平均节省了 **52%** 的能源，减少了 **38%** 的碳排放，并为客户降低了 **61%** 的成本，同时还能满足延迟要求。

#### **第二章：背景知识 - 磨刀不误砍柴工**

在深入 DynamoLLM 的设计之前，我们先要了解几个基本概念，这对于理解后续内容至关重要。

1.  **LLM 推理的两个计算阶段 (Computational phases of LLMs):**
    *   **Prefill (预填充) 阶段**：这是处理用户输入（prompt）的阶段。输入的所有 token 会被并行处理，生成第一个输出 token 的内部状态。这个阶段是 **计算密集型 (compute-intensive)** 的，它的耗时与输入 token 的数量成正比。
    *   **Decode (解码) 阶段**：这是逐个生成输出 token 的阶段。每生成一个新 token，都需要依赖前面所有（输入+已生成）的 token。这个过程是 **串行的、自回归的**，也是 **访存密集型 (memory-intensive)** 的，它的总耗时与输出 token 的数量成正比。

> **一句话总结**：Prefill 像“读题”，一次性读完；Decode 像“答题”，一个字一个字往外蹦。

2.  **性能指标 (Performance metrics for LLMs):**
    *   **TTFT (Time To First Token)**：首字延迟。用户发送请求后，到收到第一个输出 token 的时间。这直接影响用户的“体感”响应速度。
    *   **TBT (Time Between Tokens)**：字间延迟。生成每个新 token 之间的平均时间。TBT 越小，感觉模型“打字”速度越快。
    *   **SLO (Service Level Objective)**：服务等级目标。比如，我们要求 99% 的请求 TTFT 必须小于 500ms。

3.  **LLM 并行技术 (LLM parallelism):**
    *   当一个模型太大，一张 GPU 显存装不下，或者单卡算力不够时，就需要多卡并行。
    *   **张量并行 (Tensor Parallelism, TP)**：将模型内部的算子（比如矩阵乘法, $W_Q$）切分到多张 GPU 上。这些 GPU 之间需要高带宽连接（如 NVLink）进行频繁通信。论文中提到的 TP2, TP4, TP8 就是指用 2/4/8 张 GPU 来进行张量并行。

##### **D. 重配置的开销 (Reconfiguration Overheads)**

#### **第四章：DynamoLLM 的设计与实现**

基于以上洞察，作者设计了 DynamoLLM 框架。其核心是 **分层控制 (Hierarchical Control)** 架构。

![](Pasted%20image%2020260309225905.png)

*   **[图 5: DynamoLLM 架构图]**

整个系统分为三层控制器，各司其职，像一个管理有序的公司：

1.  **集群管理器 (Cluster Manager) - “公司 CEO”**
    *   **职责**：接收所有用户请求，预测它们的输入/输出长度类型，然后将它们分发到对应的“请求池”中。
    *   **决策**：**Scale-out/in**。它根据对未来负载的预测，决定为每个请求池分配多少台服务器（节点）。
    *   **频率**：每 30 分钟决策一次。

2.  **池管理器 (Pool Manager) - “部门经理”**
    *   **职责**：管理一个特定请求类型（比如“中等输入-长输出”）的所有服务器。
    *   **决策**：**Shard-up/down**。它决定池内的服务器应该采用哪种张量并行（TP2, TP4, TP8）以及如何组合。例如，一个池有 2 台 8 卡服务器，它可以配置成 4 个 TP4 实例，或者 2 个 TP8 实例。
    *   **频率**：每 5 分钟决策一次。
3.  **实例管理器 (Instance Manager) - “项目组长”**
    *   **职责**：管理单个 LLM 服务实例（比如一个 TP4 实例）。
    *   **决策**：**Scale-up/down**。它根据当前实例的排队情况，精细地调整 GPU 的运行频率。
    *   **频率**：每 5 秒决策一次。

**这个分层架构的好处是什么？**
它将一个复杂的全局优化问题，分解成了三个不同时间尺度、不同粒度的局部优化问题，大大降低了决策的复杂度和开销。高层控制器为低层设定约束，低层在约束内进行快速、精细的调整。

##### **如何降低重配置开销？**

DynamoLLM 还实现了一系列精巧的技术来“隐藏”或“最小化”前面提到的重配置开销。

*   **智能扩容 (Scaling in/out)**：
    *   在集群内部缓存模型权重，避免从远端重复下载。
    *   使用预先配置好的虚拟机快照，实现快速启动。
    *   基于负载预测，**提前** 在后台启动备用虚拟机，等高峰期到来时可以“无缝”接管流量。
*   **智能重分片 (Sharding up/down)**：
    *   **[图 6: 从 TP4 重分片到 TP2 和 TP8 的示例]**
    *   **[表 VI: 不同重分片操作的开销]**
    *   当并行度变化时（比如从 TP4 -> TP8），它不是粗暴地重新加载所有权重。它会计算出最小的数据迁移方案，只移动必要的部分权重，并且利用 GPU 间的 NVLink 高速互联直接传输，绕过 CPU 和内存，速度极快（几十到一百毫秒级别）。
*   **高效频率调整**：将 `nvidia-smi` 监控程序常驻内存，避免了每次调整频率时重新加载程序的开销。

##### **预测式调度与错误处理**

*   DynamoLLM 使用一个轻量级的 BERT 模型来预测请求的输出长度是“短、中、还是长”，准确率达到了 81%。
*   **如果预测错了怎么办？**
    *   **高估了（比如把短输出预测成长输出）**：请求会被送到一个高性能的池子，虽然浪费了点能源，但性能肯定满足 SLO。
    *   **低估了（比如把长输出预测成短输出）**：请求被送到低性能池子，可能会超时。这时实例管理器会触发“应急预案”：
        1.  优先处理队列中快要超时的请求。
        2.  立刻将 GPU 频率拉到最高。
        3.  如果还不行，就把新来的请求“重定向”到其他更合适的池子。

> ### A. 为极致能效配置实例：寻找“最优解”的数学题 (Configuring Instances for Energy-Efficiency)
> 
> 在调度之前，系统得先知道：**“面对当前的请求量，我到底该用几张卡、跑多少频率，才是最省电的？”**
> 
> DynamoLLM 采用的是一种**数据驱动 (Data-driven)** 的白盒方法。它不需要懂大模型内部复杂的 Transformer 结构，而是直接通过“压测”来生成一份**“能耗-性能画像 (Profile)”**。
> 
> #### 1. 建立“画像库” (Generating LLM profiles)
> 当部署一个新模型时，DynamoLLM 会在后台跑一遍测试。它会遍历不同的并行度（TP2, TP4, TP8）和不同的 GPU 频率（800MHz 到 1980MHz，步长 200MHz），在各种负载压力下记录两个数据：**能耗**和**延迟 (TTFT/TBT)**。
> 测试完后，系统就得到了两个数学函数：
> *   $Energy_{TP_i, f_i}(L)$：在并行度为 $TP_i$、频率为 $f_i$ 的情况下，处理负载 $L$ 预计消耗的能量。
> *   $Performance_{TP_i, f_i}(L)$：在上述配置下，处理负载 $L$ 的预计延迟。
> 
> #### 2. 全局最优解的数学表达 (混合整数线性规划 MILP)
> 有了画像，DynamoLLM 就可以把“如何配置最省电”转化成一个标准的数学优化问题：**混合整数线性规划 (MILP)**。
> 
> 假设系统当前总共有 $N$ 张 GPU，预期要处理的总负载是 $L$，延迟要求是 $SLO$。求解器需要输出：
> *   $N_{TP_2}, N_{TP_4}, N_{TP_8}$：分别需要创建几个 TP2、TP4、TP8 的实例。
> *   $f_{TP_2}, f_{TP_4}, f_{TP_8}$：这些实例分别运行在什么频率。
> *   $L_{TP_2}, L_{TP_4}, L_{TP_8}$：分配给这些实例的负载量。
> 
> **优化目标：**
> 最小化总能耗 $E$：
> $$ \min \sum_{i \in \{2, 4, 8\}} \left( N_{TP_i} \times Energy_{TP_i, f_i}(L_{TP_i}) \right) $$
> 
> **约束条件：**
> 1. **显卡数量不超标**：所有实例占用的 GPU 总数不能超过 $N$。
>    $$ \sum_{i \in \{2, 4, 8\}} i \times N_{TP_i} \le N $$
> 2. **任务必须干完**：分配给所有实例的负载总和，必须大于等于预期总负载 $L$。
>    $$ \sum_{i \in \{2, 4, 8\}} (N_{TP_i} \times L_{TP_i}) \ge L $$
> 3. **延迟不能违规**：在分配的负载下，性能必须满足 SLO。
>    $$ Performance_{TP_i, f_i}(L_{TP_i}) \le SLO $$
> 
> > **现实的骨感**：如果每次有请求来，都跑一遍这个复杂的 MILP 方程，求解大概需要 **几百毫秒**。对于要求毫秒级响应的 LLM 推理来说，**算法本身的开销比推理还慢，这是不可接受的！**
> 
> 怎么办？作者使用了一个非常聪明的策略：**分而治之（分层控制）**。
>

> ### B. 动态负载的分层控制：把大波浪化作小涟漪 (Hierarchical Control for Dynamic Load)
> 
> 既然全局最优解算得太慢，DynamoLLM 就放弃了“一步到位”，而是将这个巨大的数学题拆解成了三个在不同时间尺度上运行的“子任务”。每个层级都做一些**降维假设**，从而极大地简化了计算。
> 
> #### 层级 1：集群管理器 (Cluster Manager) —— 宏观调控，30分钟一次
> *   **任务**：**Scale-out/in**（决定用几台服务器）。
> *   **算法逻辑**：它假设所有底层机器都会以**最高性能状态**（TP8并行，1980MHz满频）运行。
>     它使用历史数据预测出未来某类请求（比如短请求）的峰值负载 $PL$。假设一台机器在满血状态下能处理的最大负载是 $ML$，那么它就分配 $\lfloor PL/ML \rfloor$ 台机器给这个请求池。
> *   **神仙细节：处理碎片化 (Handling fragmentation)**
>     如果 $PL/ML = 2.8$，系统应该分配 3 台机器吗？**不！** DynamoLLM 会向下取整分配 **2 台**机器。
>     那剩下 0.8 的负载怎么办？它会把这 0.8 的负载**转移给处理更大请求（比如中等请求）的资源池**。
>     为什么这么做？因为如果给每个池子都多分配一台机器来兜底，整个集群会有大量机器处于吃不饱的“碎片化”闲置状态。把零星的负载向上合并，可以保证只有最大的资源池有一点冗余，极大地提高了集群整体的资源利用率！
> 
> #### 层级 2：池管理器 (Pool Manager) —— 排兵布阵，5分钟一次
> *   **任务**：**Shard-up/down**（决定这几台机器怎么切分模型，比如切成 TP2 还是 TP4）。
> *   **算法逻辑**：它接收了集群管理器分配好的 $N$ 张卡。为了简化等式 (1)，它**假设 GPU 频率固定在最高值 (1980MHz)**。
>     现在，等式 (1) 中的变量去掉了频率，只剩下并行度组合（比如 8 张卡是切成 4 个 TP2 还是 1 个 TP8）。它通过快速求解这个简化版的等式，找出能耗最低的切分方案。
> *   **降级停机策略 (Reducing downtime)**：切分模型是要停机的。池管理器不会让所有机器同时停机重组，而是采用**交错滚动更新 (staggered reconfiguration)**。先更新一部分，让另一部分继续顶着流量，确保服务不断线。
> 
> #### 层级 3：实例管理器 (Instance Manager) —— 微操大师，5秒钟一次
> *   **任务**：**Scale-up/down Frequency**（调节 GPU 频率）。
> *   **算法逻辑**：这已经是最小颗粒度了。在这个瞬间，机器数量固定了，并行度（TP）固定了，连当前瞬间的真实负载也知道了。
>     它只需拿着这些已知条件去查阅“画像库”。首先，把那些会导致延迟超过 SLO 的频率过滤掉；然后，在剩下的“安全频率”里，直接挑选一个耗电最少的设定上去。
> 
> > **小结**：通过 30分钟(定机器) -> 5分钟(定并行) -> 5秒钟(调频率) 的分层策略，DynamoLLM 完美避开了复杂的全局计算，实现了极其轻量、近乎实时的动态调度。
>

> ### C. 扫清重配置的障碍：丝滑切换的工程黑魔法 (Reduced Overheads for Smooth Reconfiguration)
> 
> 算法再好，如果切换配置（比如更改 TP 并行度）需要停机 2 分钟，那动态调度就是个笑话。这部分的工程实现，是论文中最精彩的技术硬核。
> 
> DynamoLLM 针对三种操作，逐一击破了延迟瓶颈。
> 
> #### 1. 应对机器增减 (Scaling in/out) 的延迟：预判施法
> 新建一台云端 GPU 虚拟机并加载百亿参数模型，通常需要 6-8 分钟。
> *   **本地缓存**：DynamoLLM 把庞大的模型权重直接缓存在集群本地存储，免去了漫长的网络下载。
> *   **内存快照**：它保存了推理引擎初始化完成后的 VM 状态快照，启动时直接拉起，跳过繁琐的引擎启动过程。
> *   **后台预热**：更绝的是，集群管理器会**预测**下一个周期的负载。如果预测到马上要引来早高峰，它会**提前在后台启动好虚拟机**。等 epoch 切换时，流量直接打过去，用户实现**零感知**。
> 
> #### 2. 应对重分片 (Sharding up/down) 的延迟：无缝搬家算法
> 调整并行度（比如从 4 张卡 TP4 变成 8 张卡 TP8）最耗时的是在 GPU 之间重新分配那几十 GB 的模型权重（Weights）。传统的做法是：把权重从 GPU 卸载到 CPU 内存 $\to$ 重新计算切分 $\to$ 再从 CPU 传回新的 GPU。这慢得令人发指。
> 
> DynamoLLM 提出了两招：
> *   **招式一：NVLink 直传**。彻底绕开宿主机 CPU 和内存，直接利用 GPU 之间的 NVLink 高速通道互传权重。
> *   **招式二：图匹配算法 (Graph-matching algorithm) 最小化传输量**。
>     系统把当前的 GPU 和未来的 GPU 状态看作一个二分图，跑一个最大权匹配算法，目的是**“让尽可能多的权重留在原地不动”**。
> 
> > **举个具体的例子 (参考论文图 6 和 表 VI)：**
> > ![](Pasted%20image%2020260309231108.png)
> > **场景 A：从 TP4 扩大到 TP8 (升配)**
> > 初始状态：GPU 0, 1, 2, 3 组成了 TP4，每张卡手里有 **1/4** 的模型权重。
> > 目标状态：GPU 0 到 7 组成 TP8，每张卡只需要 **1/8** 的权重。
> > **DynamoLLM 的做法**：GPU 0 到 3 根本不用清空自己！它们本来就有 1/4，只需把自己手里的**一半**（即整个模型的 1/8）直接顺着 NVLink 扔给闲置的 GPU 4 到 7 即可。
> > 4 个传输动作（0 $\to$ 4, 1 $\to$ 5, 2 $\to$ 6, 3 $\to$ 7）同时**并行**发生。传输 1/8 的权重（记为耗时 $\tau$，大约 50ms），瞬间完成！
> > 
> > **场景 B：从 TP4 缩小到 TP2 (降配)**
> > 初始状态：GPU 0, 1, 2, 3 每人手里有 **1/4**。
> > 目标状态：只需要两张卡（假设选定 GPU 0 和 2），每人手里要有 **1/2**。
> > **DynamoLLM 的做法**：GPU 0 和 2 待着别动。让 GPU 1 把自己的 1/4 传给 GPU 0；让 GPU 3 把自己的 1/4 传给 GPU 2。
> > 两个动作并行，GPU 0 和 2 手里变成了 1/4 + 1/4 = 1/2。搞定！
> 
> 此外，对于内存的管理，如果在重分片期间，旧的权重和新的权重总和没有超过 GPU 显存上限，DynamoLLM 甚至允许**旧实例在后台同步数据的同时，前端继续处理着旧的请求**，把停机时间压缩到极限。
> 
> #### 3. 应对调频 (Frequency scaling) 的延迟：特权常驻
> 哪怕是单纯调低 GPU 频率（通过调用 `nvidia-smi`），操作系统频繁进行用户态/内核态切换和加载驱动，也会带来 50-80ms 的延迟，这足以让处理单个 token（通常只需 20ms）的效率腰斩。
> *   **解决方案**：DynamoLLM 把 `nvidia-smi` 监控程序直接死死地**常驻在内存中**，并且让控制器运行在**特权模式 (privileged mode)** 下。这样一来，每次 5 秒一次的调频指令可以直接穿透直达底层，彻底消除了操作系统层面的上下文切换开销。
>

## 7. throttLL’eM

三大计算障碍：

1. **自回归性质 (Autoregressive Nature)**：LLM 像写作文一样，一个词一个词地蹦。因为生成长度不可控，很难预先分配计算资源。 =》 主要指的是不同请求的总长度是未知的，LLM一般输出到自己输出结束符为止。

2. **动态批处理 (Dynamic Batch Composition)**：为了提高吞吐，服务会将不同请求合在一起跑。但批大小（Batch Size）变化会导致性能大幅波动（延迟抖动高达 45%）。

然后由于vllm的设计：

因为大家的请求长度都不一样，系统为了不让 GPU 闲着，允许新的请求在当前批次正在处理时动态地加入或退出 。这就导致 GPU 每一刻处理的“并发请求数”（Batch Size）都在剧烈波动，进而引发性能和耗电量的巨大差异 

这里指的是不一定有外面新的请求在排队，所以此时batch_size就会变小）


3. **可变的内存占用 (Variable Memory Footprint)**：KV Cache（保存上下文信息的内存）随生成长度动态增长。这种“内存墙”问题会导致性能显著下降。

LLM 每次生成新词时，都必须动态地为不断增长的序列长度保留内存（也就是 KV Cache），并且只有在请求全部完成时才释放 。这意味着生成第 10 个词和生成第 500 个词时，系统需要读取的内存数据量是完全不同的，越往后系统越被内存拖累。

不可行的传统方案：
1. 传统方案一：静态功耗限制 ，就是给服务器或 GPU 设定一个“硬性耗电上限” 。你可以把它想象成给 GPU 发放了“每日固定预算”。无论 GPU 接到多少活儿，它的整体功耗绝对不能超过这个设定值（比如限制在 250W）。
2. 传统方案二：竞速休眠 (Race-to-idle)
**它原本是什么？** 这是一种非常经典的节能策略 。它的核心逻辑是：“长痛不如短痛”。 当任务到来时，系统不计功耗代价，直接把 CPU/GPU 频率拉到最高（Race），用最快的速度把任务秒杀掉；任务一做完，立刻让硬件进入极低功耗的深度睡眠状态（Idle）以节省电量。只要“休眠”的时间足够长，整体算下来就是省电的。对于处理网页请求、短小的数据库查询等“瞬间就能做完”的任务，这招简直完美。

**为什么它在 LLM 面前失效了？**

LLM 推理完全不吃这一套，原因有两点：

1. **任务时间太长**：LLM 生成一段几百字的回答，通常需要耗费好几秒甚至十几秒。这根本不是能被“瞬间秒杀”的任务 。
    
2. **永远排队的流水线**：论文作者分析了真实的 LLM 线上流量日志，发现请求是一个**连续不断的流**（Continuous stream of requests）。日志显示，哪怕是在流量最低谷的时刻，系统每秒也至少有 1 个请求在跑 。

> 你看一下你的 `Requirements.pdf` 中的 **Task 4a (GPU Frequency)**：实验要求你手动锁定 GPU 的不同频率，然后去观察吞吐量和每个 token 的能耗（J/token）。
> 
> 如果你发现，把 GPU 频率拉到最高（也就是 Race-to-idle 策略的做法），其能效（J/token）反而不如稍微降低一点频率时的能效好，那么你就在实验中亲手证明了：**对于 LLM 这种持续不断的计算流，“全速狂飙”是最愚蠢的耗能方式。** 这也正是这篇论文提出要根据负载**“动态寻找最佳频率甜点”**的核心逻辑。

### 相应的推理的实验：

这部分的核心目标只有一个：找出到底是哪些因素在影响 LLM 推理的性能和耗电量，以及它们之间存在怎样的权衡（Trade-offs）。

作者测试了从 1 到 32 不等的 Batch Size，以及不同的 GPU 频率 。结论非常精彩（这直接对应你的 **Task 4a 和 4b**）：

![](Pasted%20image%2020260310122050.png)


- **吞吐量 (Throughput)**：毫无悬念，<u>Batch Size 越大、GPU 频率越高，系统的整体吞吐量（TPS，每秒生成的 Token 数）就越高 </u>。(为什么？batch size越大，parallelism越大，TPS就越大)

- **延迟 (Latency)**：这里出现了分歧。提高 GPU 频率能有效降低端到端延迟（E2E）和词间延迟（TBT） 。但是，**盲目增大 Batch Size 会导致E2E和TBT延迟恶化**，因为更多的并发请求会导致 GPU 内部的资源竞争加剧 。

- **功耗 (Power)**：这是一个极其关键的发现！**对于给定的 GPU 频率，无论 Batch Size 是 1 还是 32，功耗几乎保持不变** 。功耗主要受 GPU 工作频率的直接影响 ,<u>GPU 频率越大，功率越大</u>。

- **能效 (Energy Efficiency)**：作者用“每焦耳生成的 Token 数 (TPJ)”来衡量能效 。因为大 Batch Size 下功耗不变但产出变多，所以**处理更大的批次总能提高能效** 。更反直觉的是，**并非频率越低越省电** 。实验发现了一个“甜点区”（比如 1050 MHz）：使用最大 Batch Size 配合 1050 MHz 的较低频率，能在对性能影响极小（吞吐量仅下降 6.25%）的情况下，实现高达 **37.4%** 的能效提升 。


> **给你的实验避坑指南**：在做 Task 4a 时，如果你把频率降得太低（比如低于 840 MHz），你会发现虽然瞬时功率（瓦特）降了，但因为算得太慢，完成任务花费的总时间大幅拉长，最终计算出的每 Token 能耗（J/token）反而变差了

## 2. KV Cache：潜伏的“性能杀手”

在推理生成阶段，系统需要不断为新生成的词分配 KV Cache。作者发现它对系统有着绝对的统治力：

- **吞吐与延迟的双重打击**：随着分配的 KV Cache 块数量增加，系统的吞吐量会出现明显的下降，同时词间延迟（TBT）呈现**线性上升** 。
    
- **吃掉更多电量**：由于每次迭代需要从显存（DRAM）中读取的数据量越来越大，**KV 块与功耗之间存在正相关关系** 。而且在高频率下，这种耗电的增长速度会更快 。
    
- **神仙级发现（完美替身）**：作者经过统计发现，KV Cache 的使用量与词间延迟（TBT）的皮尔逊相关系数高达 **0.92**，与吞吐量的相关系数高达 **-0.92** 。这意味着，**我们可以直接把 KV Cache 的占用量当作预测系统性能的“晴雨表”** 。这也是为什么后续的 throttLL'eM 框架要死磕“预测 KV Cache”。

具体来说：

- **Figure 3a (KV Cache vs. 吞吐量 Throughput)**：
    - **坐标轴含义**：横坐标是分配的 KV Cache 块数量（KV blocks [#]），纵坐标是系统的吞吐量（以每秒迭代次数 IPS 衡量） 。
    - **图表内容**：图中绘制了多条曲线，分别代表不同的 Batch Size（4、8、16、32） 。
    - **核心现象**：可以清晰地看到，随着 KV Cache 块数量的增加，吞吐量下降，TBT上升；clear degradation in Throughput and a linear increase in TBT  所有 Batch Size 下的吞吐量都出现了**明显的下降（degradation）** 。
        
- **Figure 3b (KV Cache vs. 词间延迟 TBT)**：
    - **坐标轴含义**：横坐标同样是 KV Cache 块数量，纵坐标是词间延迟（TBT，单位是毫秒 ms） 。
    - **核心现象**：随着 KV Cache 块数量的增加，词间延迟TBT呈现出**线性上升**的趋势 。
- Figure 3c 的结论：KV Cache 越多，系统越“费电”

作者测试了在固定 Batch Size（32）下，随着生成过程不断推进（即 KV 块数量不断增加），不同 GPU 频率下的功耗表现 。

- **功耗与 KV 大小正相关**：在所有频率下，随着 KV Cache 块的增加，功耗都在同步上升 。作者指出，这是因为每次迭代时系统需要从 DRAM（显存）中读取的数据量变大了，导致物理级别的耗电增加 。
- **高频下的“耗电惩罚”更严重**：这是个非常有趣的现象！曲线显示，在较高的 GPU 频率下，随着 KV 块的增长，功耗上升的坡度（斜率）变得更陡峭了 。这意味着在高频下，每多增加一个 KV 块，系统需要付出的功耗代价比低频时大得多 。
- **核心启发**：这种梯度上的差异告诉我们，要想实现最优的能效，就必须把“KV Cache 的管理”和“GPU 频率的缩放（调频）”结合起来精打细算 。
    

- Figure 3d 的结论：KV Cache 是性能的“完美替身”（KV Cache的使用量和TBT直接相关）

为了进一步验证 KV Cache 和性能（吞吐量、延迟）的关系，作者做了一个长达 200 秒的动态实验：保持 Batch Size 为 32，旧请求一完成就立刻塞入新请求（生成长度随机），且保持 GPU 频率在最高档位 。

- **神同步的曲线**：实验图表显示，KV Cache 的使用量曲线和词间延迟（TBT）曲线几乎完全重合，表明它们之间存在直接的关系 。同时，系统的吞吐量曲线看起来就像是 KV Cache 使用量曲线的“镜像（倒影）” 。
    
- **惊人的相关系数**：通过统计学分析得出，KV Cache 占用量与词间延迟（TBT）的皮尔逊相关系数高达 0.92 。而 KV 与吞吐量之间的相关系数高达 -0.92 。如果在更小的 Batch Size 下重复实验，这个相关性还会进一步提高，因为受新请求“预填充（Prefill）”阶段干扰导致的生成停滞变少了 。
    
- **核心启发**：由于它们之间的相关性极高，因此完全可以把 **KV Cache 的使用量作为精确建模系统性能的核心代理指标（Proxy）** 。这正是后面系统能够提前预测并防止服务卡顿的理论基石！

**这两张图共同传递的几个关键结论**：

1. **趋势的一致性**：无论你设定多大的 Batch Size，这种“KV Cache 变大导致性能恶化”的趋势都是一致存在的 。
2. **小 Batch Size 的相对优势**：如果在**相同的 KV Cache 块数量**下进行横向比较，**较小的 Batch Size 反而能取得更好的性能** 。作者解释说，这是因为小 Batch 在每次迭代时需要生成的 token 较少，从而减少了 GPU 内部的资源竞争 。

如果在 **单台物理服务器节点内**
#### 1. 性能擂台赛：张量并行（TP）是单节点内的绝对王者

**Figure 4a (Throughput vs. batch size)** 展示了不同并行策略在不同并发数下的吞吐量（TPS）表现。

- **全面碾压的吞吐量**（TPS）：图中的紫色曲线代表张量并行（TP）。你可以明显看到，无论是 2 卡（TP2）还是 4 卡（TP4），TP 的曲线都高高在上，始终碾压同等卡数的 DDP（绿色）和 PP（红色）。具体来说，在最大支持的 Batch Size 下，TP 的吞吐量比 DDP/PP 高出 1.54倍 到 6.26倍 不等 。

- **为什么会这样？** 增加并行度（增加 GPU 数量）自然会带来更多的计算资源，但更重要的是，多张卡汇聚了**更大的显存容量** 。TP 将模型的权重矩阵切分到多张卡上，使得单张卡上驻留的模型权重变小了。省下来的显存去了哪里？全部拿去放 **KV Cache** 了！有更多的 KV Cache 块，系统就能同时塞入更多的请求（即更大的 Batch Size），从而极大地拉升整体吞吐量 。

> [!note]-
> 如果在现实中无脑选 TP，遇到大集群部署时肯定会踩大坑。这篇论文之所以在这个章节得出“TP 完胜”的结论，是因为有一个极其严苛的大前提被隐藏在字里行间了：这里的测试仅仅局限于“单台物理服务器节点内（Intra-node scaling）” 。
> 
> 除了吞吐量和能效，选择切分策略时，硬件底层的通信带宽和集群的物理规模才是真正起到决定性作用的因素 。我们来把 DDP 和 PP 真正的用武之地找回来：
> 
> 1. TP 的致命软肋：跨不出的“单机魔咒”
> TP（张量并行）的本质是把一个巨大的矩阵乘法暴力切开，让几张显卡同时算，算完后必须立刻把结果汇总。
> 
> 
> 代价是什么？ 这要求显卡之间的数据交换速度快到令人发指 。在单台机器里，有 NVLink 这种极其昂贵的高速互连技术撑腰，TP 才能起飞 。
> 
> 
> 瓶颈在哪？ 一旦你想跨越物理机（比如用网线连起来的两台服务器）使用 TP，极其缓慢的跨机网络延迟会直接把系统拖垮。因此，论文明确指出，TP 可能根本无法扩展到单节点之外 。
> 
> 2. PP (流水线并行) 的主场：超大模型的“接力跑”
> 如果一个大模型（比如拥有数千亿甚至万亿参数）实在太庞大，连单台顶配服务器的 8 张卡都塞不下，该怎么办？
> 
> 这时候就必须跨节点部署了 。
> 
> 论文的讨论部分明确提到，对于需要跨节点分布的更大型模型，PP 通常用于节点间（Inter-node）的通信，而节点内（Intra-node）依然使用 TP 。这就像一条跨越多个车间的流水线，机器之间用 PP 传递中间结果，机器内部用 TP 加速局部计算。
> 
> 3. DDP (数据并行) 的主场：应对海量并发的“分身术”
> Figure 4 里 DDP 表现拉垮，是因为作者强行用它来处理单个大模型的内部切分。但在真实的云服务中，DDP 是用来做实例扩展的。
> 
> 如果你的机器显存足够大，能完整装下一个模型，而外面的用户请求（RPS）多得像洪水一样，你该怎么办？
> 
> 论文指出，throttLL'eM 框架与 DDP 其实是正交的（互不冲突），像其他并行工作就会使用 DDP 来部署多个 LLM 实例 。也就是说，你会用 DDP 直接复制出好几个一模一样的 LLM 引擎，大家各算各的请求，互不干扰，完美消化海量流量。
> 
> 总结一下：
> 单看这篇论文的 Figure 4，确实只比拼了吞吐量和能效，TP 赢麻了。但在真实世界的工程架构中：
> 
> 
> TP 负责单机内部的极致加速 。
> 
> 
> PP 负责跨越机器的显存拼接 。
> 
> 
> DDP 负责复制实例以扛住海量并发流量 。
> 
> 所以，三者绝不是谁替代谁的关系，而是针对不同硬件规模和流量压力的“组合拳”。


#### 2. 能效的反直觉真相：算力并非“越多越省”

这部分是整篇文章在“节能”主题上的核心洞察，也就是 **Figure 4b (Efficiency vs. batch size)** 所揭示的现象。

- **TP 依然是最省电的策略**：在能效（每焦耳生成的 Token 数，TPJ）方面，紫色的 TP 曲线依然处于最高位 。
    
- **“小马拉大车”最省电**：仔细看 Figure 4b 中的紫色虚线（TP2）和紫色实线（TP4）。在 Batch Size 较小的时候（比如 Batch Size 在 1 到 16 之间），**2 张卡的 TP2 的能效（TPJ）居然比 4 张卡的 TP4 还要高出最多 9.66%！**
    
- **为什么卡少了反而能效高？** 这是因为每点亮一张 GPU，就会带来固定的基础静态功耗。如果你当前的实际流量很小（Batch Size 很低），4 张卡处于“吃不饱”的半饥饿状态，算力被浪费了，但 4 张卡的底噪功耗依然在烧电。相比之下，用 2 张卡去跑同样的低负载，虽然算得稍微慢一点点，但省下了整整两张卡的静态功耗，整体算下来（Tokens/Joule）反而更加划算。作者得出的结论是：**在能够支撑当前 Batch Size 的前提下，应该尽可能优先使用规模更小的引擎来优化能效** 。

### 3. 核心启示：走向“动态引擎缩放”（Autoscaling）

这段文字最后的带星号的总结（Takeaways）点明了这部分存在的根本目的：

在单台机器（节点内）横向扩展时，无脑选 TP 就对了，它在性能和能效上都是最优解 。

但是，**不同并行度（用几张卡）在性能和能效之间存在 Trade-off（权衡）** 。流量低时，小引擎（TP1, TP2）更省电；流量爆发现象时，大引擎（TP4, TP8）吞吐量更大且不卡顿。这就引出了论文在第四部分（Section IV.D）提出的核心机制：**基于实时工作负载特征的动态引擎大小调整（Autoscaling）** 。系统不能死板地一直开着 8 张卡，而是必须根据当前的 RPS（每秒请求数）动态地增减活跃的 GPU 数量。
### 4. 真实的线上流量到底有多“野”？

为了证明实验室里的推论在真实世界中站得住脚，作者抓取了 Azure 真实的 LLM 推理日志 。

- **极其长尾的分布**：用户输入的 Prompt 和模型生成的回复长度，差异极大。提示词最长到了 4000 个 Token，而绝大多数在 0-1500 之间 。这种巨大的随机性，证实了我们第一期讲的“静态资源分配”根本行不通 。
    
- **机器永不休眠**：按 4 分钟一个统计窗口来看，即使在流量最低谷，系统每秒钟（RPS）也至少要处理 1 个请求 。这就彻底宣判了传统“竞速休眠 (Race-to-idle)”策略在 LLM 时代的死刑 。

## 1. throttLL'eM 框架总览 (System Overview)

当一个新用户的请求（Query）到达系统时，它会经历以下一套精密的流水线 ：

1. **生成长度预测**：首先，系统会猜一下这个请求大概会生成多少个 token 。(文章对当前的模型 进行了分类，有分类法、回归法、提前感知法)，但是论文中没有给具体模型，只是拿之前有的模型（误差率30%左右）预测 $q_a \rightarrow \text{生成长度} |\hat{r_a}|$ 
    
2. **KV 缓存与批大小投影**：基于上一步的预测，系统在脑海中“模拟”出未来每一毫秒的 KV Cache 占用量和 Batch Size 变化 。引入Scoreboard

这个时候系统拿到了这个请求会生成多长的token 

Scoreboard是计算机arch中的概念

> [!note]+ 算法
> 1. 核心数据结构：记分板 (Scoreboard)
> 你可以把记分板想象成餐厅后厨的“订单追踪大屏”。针对当前正在 GPU 里跑的每一个请求 $q_i$，记分板上都会记录三项元数据（Metadata）：

- $s_i$：这个请求是被调度的起始迭代时刻。
- $|q_i|$：这个请求的输入提示词长度（Prompt length）。
- $|\widehat{r_i}|$：这个请求的预测生成长度（也就是上一期我们得到的那个预测值）。有了这三个已知量，系统就能算出这个请求的“死期”：它将在 $s_i + |\widehat{r_i}|$ 这个时刻完成生成并退出。

2. 推演一：预测未来的 Batch Size ($B$)

既然我们知道了记分板上所有请求的起始时间和预计结束时间，那么对于未来任意一个时刻 $j$，我们只要数一数“<u>在这个时刻，还有多少个请求没结束</u>”，就能得到时刻 $j$ 的预测批大小 $B_j$。把未来所有时刻的批大小连起来，就得到了向量 $B$。这个过程纯靠简单的加减法，计算极快。

3. 推演二：预测未来的 KV Cache 占用 ($KV$)

这是最关键的计算。作者用两个极其优雅的数学公式解决了显存预测问题。

首先看单个请求在未来时刻 $j$ 会吃掉多少显存。在 PagedAttention 的机制下，KV Cache 是按“块（Block）”来分配的，假设每个块能装 $N$ 个 token。

公式 (1) 拆解：$$KV_{q_i}[j] = \begin{cases} \lceil (j - s_i + |q_i|) / N \rceil, & s_i \le j < (s_i + |\widehat{r_i}|) \\ 0, & \text{otherwise.} \end{cases}$$别被公式吓到，它的物理意义极其直白。看分子的部分：

- $(j - s_i)$：代表从开始到时刻 $j$，系统已经为它新生成了多少个 token。
- $+ |q_i|$：代表一开始就存在的输入提示词的 token 数量。这两者相加，就是时刻 $j$ 该请求总共的上下文长度。把它除以每个块的容量 $N$，然后向上取整 $\lceil ... \rceil$，就算出了这个请求在时刻 $j$ 需要霸占多少个 KV 块。

后面跟的条件语句只是说：如果这个请求还没开始，或者已经结束了，那它的占用量就是 $0$。

公式 (2) 拆解：$$KV[j] = \sum^{\forall q_i} KV_{q_i}[j]$$这就更简单了。把时刻 $j$ 记分板上所有请求的 KV 块占用量加在一起，就是整个推理引擎在未来时刻 $j$ 的总 KV Cache 占用预测值。

4. 灵魂机制：虚拟追加 (Virtual Append)

推演未来有什么用呢？主要是为了防患于未然。

当一个全新的请求 $q_a$ 刚刚到达，还没被正式扔进 GPU 之前，系统会玩一招“如果在平行宇宙”的模拟：

它会把这个新请求的元数据 **“虚拟追加（Virtually appended）”** 到记分板上，假设它就在当前时刻 $k$ 开始执行。然后，系统飞速地跑一遍上面的公式，看看加入这个新兵之后，未来的 $KV$ 向量会不会在某个时刻突然撑爆 GPU 的总显存限制？

- 如果未来的显存安全，且满足其他 SLO 要求，系统才会正式让它插队，这叫提交 (Commit)。
- 如果发现未来某个时刻会炸显存（内存溢出），系统就会把这个“虚拟”记录抹掉，让请求去队列里乖乖排队，这叫回滚 (Roll back)。

性能开销：因为这套逻辑纯粹是 CPU 上的简单数学运算，没有任何复杂的张量计算，所以作者实测它的平均延迟小于 2 毫秒，对动辄几秒的大模型推理来说完全可以忽略不计。


3. **查询调度器 (Query Scheduler)**：利用模拟出的数据，系统评估如果现在把这个请求放进去，会不会导致未来的 SLO 违规（比如导致其他请求卡顿）。如果没有违规风险，就准许执行；否则，让它去排队 。
    
4. **频率与规模控制**：对于准许执行的请求，**限流控制器 (Throttling Controller)** 会计算出能满足 SLO 的最低 GPU 频率并执行；同时，**自动缩放机制 (Autoscaling)** 会根据整体流量动态增减 GPU 实例的数量 。


在传统的 LLM 服务器中（比如没有优化的 Triton），如果有 100 个请求同时涌入，系统往往会不管三七二十一全塞进 GPU。结果就是：要么显存瞬间被撑爆直接宕机（Out-of-Memory, OOM），要么大家挤在一起，生成一个词要等好几秒（严重的 SLO 违规）。

throttLL'eM 的核心哲学是：**宁可让你在门口等，也不能让你进去把场子砸了** 。

## 整个准入控制的完整流程是怎样的？

当一个新请求（Query）到达时，流程如下：

### 步骤一：虚拟推演（脑内小剧场）

门口的安保（调度器）接到新请求后，**不会立刻放行**。他会把这个新人的信息“虚拟追加（Virtually append）”到记分板上，也就是在脑海里推演一下：“如果我放他进去，未来一段时间里，夜店里的人数（批大小 $B$）和占用的卡座（KV Cache 使用量 $KV$）会怎么变？”

推演完之后，安保会拿着这份“未来的预测报告”，对这个新请求进行**三项严格的合规性检查** ：

### 步骤二：严格的“灵魂三问”（三关考核）

**第一问：未来会“内存溢出”吗？ (KV cache assessment)**

- **操作**：安保查看刚才推演出的未来 $KV$ 向量，对比一下 GPU 的物理显存上限 。
    
- **如果会溢出怎么办？**：这就是回答你的问题——**如果发现未来哪怕有任何一微秒的显存会超过容量上限，安保就会立刻举起红牌，让这个请求去“排队（Queued）”** 。
    
- **为什么要排队？**：因为如果不排队强行塞进去，GPU 显存装不下，系统就会被迫把一部分显存数据临时置换（Swap）到速度极慢的 CPU 内存里，这会导致性能呈现断崖式暴跌 。排队（Queuing）就是把这个请求暂时存放在 CPU 的等待队列里，等里面有旧请求处理完、释放了 KV Cache 显存空位后，再重新评估放它进去 。
    

**第二问：大家聊天会卡顿吗？ (TBT SLO compliance)**

- **操作**：如果显存够用（第一关过了），安保会掏出一个**性能预测机器学习模型 ($M$)** 。把未来的显存占用、批大小、系统频率等数据输进去，模型会预测出未来的“吞吐量（IPS）” 。
    
- **判定**：把吞吐量取个倒数，就得到了每个词的生成间隔时间（TBT）。如果算出来发现，放这个新人进去会导致大家生成 token 的平均时间太长，超出了系统承诺的底线（比如平均 TBT 超过 200 毫秒），那对不起，**去排队** 。
    

**第三问：会导致别人错过“末班车”吗？ (E2E SLO compliance)**

- **操作**：这一步最体现全局观。安保通过上面的 TBT 算出未来每一步到底需要花费多少绝对时间（$\hat{T_R}$）。
    
- **判定**：他要检查里面**正在跑的旧请求**。因为新人的加入会抢占算力，导致整体变慢。如果放新人进去，会导致某个已经在里面的旧请求因为被拖累，从而错过了它的端到端延迟死线（E2E Deadline），那新人一样不准进，**去排队** 。
    

### 步骤三：一锤定音（Commit or Rollback）

- **放行（Schedule）**：如果这“灵魂三问”全部顺利通过（不爆显存、不卡顿、不拖累别人），安保就会把脑内推演的结果正式写入记分板（Commit scoreboard entry），真正把这个请求送进 GPU 开始执行 。
    
- **排队（Queue）**：只要有任何一问没通过，脑内的推演结果全部作废（回滚 Roll back），请求乖乖待在等待队列里，等下个周期再试

### 第一步：接收与预处理 (顶层)

1. **用户提问**：最上方，用户输入了一个问题 $q_a$（"How to make LLMs more energy efficient?"）。
    
2. **Token化 (Query Tokenization)**：大模型不认识人类文字，所以系统首先把句子切碎并转换成一串数字 ID（图中绿色的数组）。此时，系统知道了这个请求的**输入长度** $|q_a|$ 。
    

### 第二步：算命先生 (右上角模块)

3. **Token Generation Length Prediction（生成长度预测）**：这个词元数组被送进预测模块。模块给出一个极其关键的猜测：**它预测这个请求最终会生成 $\widehat{r_a}$ 个 token** 。这就是我们之前说的“把预测当黑盒”。
    

### 第三步：沙盘推演 (左侧中部模块)

4. **KV usage & Batch Size projection（KV与批大小投影）**：现在，系统拿着新请求的已知信息（到达时间、输入长度、预测输出长度），在 **Scoreboard（记分板）**上做了一个虚线箭头的操作——**"Virtual" append（虚拟追加）** 。
    
5. **推演未来**：系统结合当前正在跑的老请求（Running queries metadata），画出了两张折线图（图中中间的两个小图）：未来的 KV Cache 占用量预测（$KV$ 向量）和未来的批大小预测（$B$ 向量）。
    

### 第四步：夜店安保 (右侧中部模块)

6. **Query Scheduler（查询调度器）**：安保人员拿着刚才推演出的 $KV$ 和 $B$ 向量，以及当前引擎规模 $E$ 和 GPU 的**最大频率** $max F$，送进绿色的虚线框——**Performance Prediction Model $M$（性能预测模型）** 。
    
7. **灵魂三问**：模型 $M$ 吐出未来的吞吐量预测 $T$ 。系统紧接着做菱形框里的判断：**SLO, KV violation?（会违规吗？）** 。
    
    - **Yes（会违规）**：走右边箭头，**Add to Queue（扔进队列排队）** 。
        
    - **No（安全）**：走下面箭头，**Schedule Query（准许调度）**，并向左发一个信号 **Commit scoreboard entry**，把刚才记分板上的“虚拟追加”变成“正式记录” 。
        

### 第五步：榨干最后一点能效 (右下方虚线框)

8. **Throttling triggering（触发调频）**：如果安保放行了，说明**在最高频率 $max F$ 下**运行是绝对安全的 。但我们是为了省电啊！所以系统进入右下角的循环虚线框。
    
9. **寻找底线**：这里是一个二分查找循环（那个打着转的箭头）。系统不断地向模型 $M$ 喂入更低的频率 $F$，重新计算 $T$，看看在满足 SLO 的前提下，频率**最低**能降到多少（**min F satisfying SLOs**）。
    

### 第六步：干活与宏观调控 (左下方模块)

10. **执行**：把上一步找到的最省电频率，下发给底层的 **Throttling Controller（调频控制器）**，统一调节所有 GPU 的频率 。然后底层的 **LLM Instance** 开始真正生成 token 。
    
11. **Autoscaling（自动缩放，右下黑色实线框）**：这是一个独立在后台跑的宏观管家。它不盯单个请求，而是盯着整体的 **RPS（每秒请求数）**。如果整体流量太大或太小，它会判断是否过了冷却期（Grace period），然后决定是加机器（scale up）还是减机器（scale down）。

查询调度器（Query Scheduler）的唯一使命，就是决定一个新请求能不能进入 GPU 执行而不搞砸别人的体验 。为了做到这一点，它高度依赖一个**性能预测模型 ($\mathcal{M}$)** 。

## 1. 性能预测模型 ($\mathcal{M}$) 是如何炼成的？

这个模型的核心任务是：预测系统在未来的吞吐量，即**每秒迭代次数 (IPS)** 。

### 训练数据的收集 (Training data collection)

想让模型预测得准，就得喂给它足够多的数据。但作者发现，直接遍历所有的参数组合是不可能的，因为 GPU 频率（15 MHz 一个步长）、KV Cache 使用量、以及最高可达 512 的批大小，组合起来的状态空间太庞大了 。

为了解决这个问题，作者采用了一种**系统化采样 (Systematic sampling)** 的方法 ：

- 他们写了一个请求生成器，专门生成特定长度的请求来塞满 GPU，确保 KV Cache 的使用量能覆盖从空到满的整个区间，触达性能的边缘 。
    
- 在收集数据时，系统每秒记录一次当前的 KV Cache 使用量、GPU 频率、批大小以及实际的 IPS 。
    
- 为了覆盖所有的频率范围，在每次测量完成后，系统会随机切换到一个新的 GPU 频率 。
    

### 模型的选择与训练 (Model selection & training)

既然拿到了数据，选什么模型来训练呢？作者没有用复杂的深度神经网络，而是选择了一个经典的传统机器学习算法：**梯度提升决策树 (Gradient Boosted Decision Tree, 简称 GBDT)** 。

- **为什么选 GBDT？** 因为 LLM 的这些特征（频率、批大小等）都是有明确上下界的，而 GBDT 在处理这种有边界且特征相互作用的数据集时，插值预测极其精准 。
    
- **天下武功，唯快不破**：这个模型最牛的地方在于它极其轻量。它在 CPU 上的推理延迟大约只有 **3 毫秒** ！因为这个模型卡在调度器的关键路径上（每次来新请求都要算一遍），如果模型太慢，预测未来就没有意义了 。
    
- **输入与输出**：模型的输入是四个维度：i) 引擎规模 (GPU 数量)；ii) 批大小；iii) KV Cache 使用量；iv) GPU 频率 。输出只有一个：预测的吞吐量 (IPS) 。

## 2. 准入控制的“灵魂三问”硬核版

拿到预测模型后，当新请求到来，调度器就会结合前面“记分板”算出的未来 $KV$ 和 $B$ 向量，进行严苛的三步审查 ：

### 第一问：KV cache 评估 (KV cache assessment)

- **逻辑**：非常简单粗暴。直接看预测出的未来 $KV$ 向量里的最大值，有没有超过 GPU 显存能容纳的 KV 块物理上限 。
    
- **底线**：如果超过了，立刻排队（Queued）。因为一旦爆显存，多出来的数据就会被置换（Swap）到慢吞吞的系统主存里，这会导致性能面临毁灭性的打击 。
    

### 第二问：词间延迟合规性 (TBT SLO compliance)

- **计算**：如果显存没爆，系统就把未来的批大小、KV 占用和**最高的 GPU 频率**丢进模型 $\mathcal{M}$ 里，模型会吐出一个未来的吞吐量向量 $T$ (里面全是 IPS 的预测值) 。
    
- **转换**：因为“每秒生成多少词 (IPS)”的倒数，就是“生成每个词需要的时间 (TBT)”，所以系统算了一个倒数：$TBT = 1/\text{IPS}$ 。这就得到了未来的词间延迟向量 $T'$ 。
    
- **底线**：如果这个向量 $T'$ 算出来的平均值超过了官方承诺的 TBT SLO 限度，请求就得去排队 。
    

### 第三问：端到端延迟合规性 (E2E SLO compliance) 与 公式 (3)

这是你截图里最复杂的一段数学公式。一旦搞懂了，逻辑其实非常优美。

**公式 (3) 拆解：**

$$\widehat{T_{R_j}} = \sum_{i=k}^{i \le j} T'_i = \sum_{i=k}^{i \le j} T_i^{-1}$$

- **物理意义**：这个公式是在计算**“到达未来某个时刻 $j$ 到底需要多长时间”** 。
    
- 我们在第二步已经得到了 $T'$（未来每生成一个词需要花费的毫秒数）。
    
- 假设当前是第 $k$ 步。我要预测走到未来的第 $j$ 步要花多久？很简单，把从 $k$ 到 $j$ 每一步的花费时间（$T'_i$）全部**累加起来（$\sum$）**就可以了 。这就是累积和（Cumulative sum）的概念 。
    

**如何判定违规？**

1. 对于当前已经在 GPU 里跑的任意一个老请求 $q_i$，系统知道它预计会在未来的第 $l$ 步结束（其中 $l = s_i + \widehat{|r_i|} - k$） 。
    
2. 通过查阅上面公式算出来的累积时间向量，就能直接得到这个老请求还需要多久才能跑完（即 $T_{R_l}$） 。
    
3. 系统把这个所需时间加上当前时间，对比老请求的“绝对截止时间 (Deadline)”。如果放新请求进来会导致老请求的时间超过 Deadline，那么新请求就不予放行 。
    

---

至此，通过一个仅需 3 毫秒的机器学习模型和几个简单的累加公式，调度器完美地预测并避开了所有的性能雷区。

> ### 一、 宏观容量控制：大模型实例自动扩缩容 (Section IV.D)
> 
> LLM 的推理引擎由于包含了庞大的模型权重，其启动（加载权重到显存、建立通信网络）是一个极其沉重的过程。论文指出，这个过程**通常需要超过 20 秒 (>20s)**。
> 
> #### 1. 扩缩容的决策依据：基于 Profile 的阈值
> 系统后台有一个 10 秒间隔的监控代理（Monitoring Agent），它监控当前的**请求到达率（RPS）**。系统如何知道何时该扩容？
> 论文通过离线压测生成了“性能画像”（如论文 Table II 所示，例如 Llama2-13B 在 TP1 下最大扛 1.125 RPS，在 TP4 下能扛 7.5 RPS）。一旦当前 RPS 逼近当前引擎配置（Tensor Parallelism, TP 数量）的极限，系统就会触发扩容。
> 
> #### 2. 掩盖 20 秒延迟的工程手段：影子实例 (Shadow Instancing)
> 为了不让这 20 多秒的启动时间导致新来的请求全部超时（SLO Violations），论文采用了无缝切换的**影子实例技术**：
> *   **Warm-up（热身阶段）：** 系统决定把 TP1 扩容到 TP2，此时 TP2 实例在后台开始启动（拉取权重等）。**关键点：** 在这 20 多秒里，所有源源不断进来的真实用户请求，依然全部由旧的 TP1 引擎承担。
> *   **Transition（交接阶段）：** 当 TP2 实例彻底准备就绪（Operational）后，旧的 TP1 引擎会优雅地停止接收新请求并处理完手上剩余的请求（Gracefully shuts down），而全新的请求将全部路由给新的 TP2 引擎。
> 
> #### 3. 核心痛点与解决：不对称的“宽限期 (Grace Period)”策略
> **痛点：** 影子实例虽然掩盖了延迟，但在那 20 多秒里，旧引擎（满载运行）和新引擎（正在启动）是**同时消耗电力的**（峰值功耗翻倍）。如果流量此时恰好在一个阈值边缘“反复横跳”（比如在 1.1 RPS 和 1.2 RPS 之间波动），系统就会陷入疯狂的“启动-销毁-启动”死循环，浪费极其惊人的电量。
> 
> **解决逻辑（宽限期）：**
> 为了把能源浪费降到最低，作者设计了一个极其聪明的规则：**给新出生的引擎发放一张“免死金牌”，时长等于它的启动时间（比如 20 秒）。**
> 在这 20 秒内，遵循**“非对称”**的调度策略：
> *   **允许 Scale-up（向上扩容）：** 如果这 20 秒内流量突然面临极其变态的洪峰（比如瞬间飙到 7 RPS），为了保住 SLO（用户体验永远第一），系统依然允许继续启动更大的引擎（如 TP4）。
> *   **绝对禁止 Scale-down（向下缩容）：** 即使这 20 秒内流量突然跌回 0.5 RPS，系统也**强行禁止**关闭新引擎退回 TP1。这不仅防止了过早缩容，更避免了刚刚耗费巨大电量拉起的影子实例白白浪费。
> *   **刷新机制：** 只要测量到的 RPS 处于当前引擎的处理能力范围内，这个宽限期就会被刷新。
>

> 
> ### 二、 微观频率操盘手：GPU 降频控制器 (Section IV.E)
> 
> 如果说 Autoscaling 是解决“需要多少张显卡”，那么 Throttling Controller 解决的就是**“这几张显卡该以多低的频率运行才能最省电”**。
> 
> 这部分的逻辑设计非常严密，分成了“排队准入（Scheduler）”和“频率寻优（Throttler）”两个阶段解耦执行。
> 
> #### 1. 调频的数学“底气”：先验保证
> 调频器（Throttling Controller）只有在请求**已经被 Scheduler 接收**后才会触发。
> 这具有重大的数学意义：Scheduler (Sec IV.C) 在进行准入测试时，传入性能预测模型 $\mathcal{M}$ 的 GPU 频率参数是 **Maximum available GPU frequency（最大频率）**。
> 如果 Scheduler 放行了，这就提供了一个逻辑学上的存在性证明：**系统在最高频率下一定能满足这个请求的 SLO。** 因此，接下来的降频搜索无论怎么失败，系统都有“最高频率”这条退路，绝对不会因为降频算法导致意外的 SLO 违规。
> 
> #### 2. 核心算法：基于预测向量的二分查找 (Binary Search)
> 调频器接手后，它拿到了系统对未来迭代状态的预测向量：未来的 Batch size 变化 ($B$) 和 KV Cache 占用变化 ($KV$)。
> 面对从低到高多个离散的 GPU 频率档位（比如 A100 从 210MHz 到 1410MHz，步长 15MHz），它执行**二分查找**：
> 1.  **取中间频率**，将该频率连同 $B$ 向量和 $KV$ 向量输入机器学习预测模型 $\mathcal{M}$。
> 2.  模型吐出在**这个特定降频下**，未来每一步的吞吐量向量 $T$ (IPS)。
> 3.  对 $T$ 取倒数，得到每一步生成一个 Token 需要的时间 $T'$ (TBT)。检查 $T'$ 的平均值是否超过了 200ms 的 SLO。
> 4.  对 $T'$ 进行累加（Cumulative Sum，即论文公式 3），得到预估到达未来每一步的绝对时间 $T_R$。检查请求完成的最终时间是否超过了端到端延迟 SLO ($t_{dead}$，公式 4)。
> 5.  如果上述测试都通过，说明这个频率安全，继续往**更低频率**的区间二分；如果测试失败（会违规），说明频率给太低了，往**更高频率**的区间二分。
> 最终，系统锁定那个**刚刚好踩在 SLO 死线上的最低可用频率**。
> 
> #### 3. 两个极具工程价值的细节
> 
> *   **木桶效应规避 (Mitigating stragglers & barrier synchronization)：**
>     大模型推理通常采用张量并行（Tensor Parallelism），意味着一个计算任务被切分在多张 GPU 上同时跑，算完一层后需要互相通信（All-Reduce）。**通信的速度取决于最慢的那张卡**。
>     因此，当二分查找算出最佳频率后，throttLL'eM 会把这个频率**强制且统一地**应用到服务该 LLM 实例的**所有 GPU 上**。这避免了因不同 GPU 频率不一致导致的屏障同步等待时间（Barrier Synchronization issues），同时也大幅降低了系统维护多个不同频率的复杂度。
> *   **尽人事听天命的“Lost”请求协议：**
>     有时候系统负载太高，新来的请求即使在最高频率下也会违规。但为了不让它永远卡在队列里饿死，Scheduler 会勉强放它进来，但给它打上“Lost（迷失/注定超时）”的标签。
>     此时，调频器一旦检测到当前 Batch 里面存在哪怕一个“Lost”请求，它会**直接放弃炫技般的二分查找降频**。它会毫不犹豫地把 GPU 频率拉满到 Maximum，以此做“Best-effort（尽力而为）”的抢救，力求把超时的程度降到最低。
> 
> **性能开销总结：**
> 这套包含了“未来状态向量投影 + ML模型推理 + 二分查找 + 检查判断”的复杂操作，因为模型轻量级且高度优化，在重负载下一次完整的调度和降频决策加起来**仅耗时约 35 毫秒 (35ms)**。考虑到 LLM 生成一个完整的回答通常需要数秒，这 35ms 带来的电量节省（论文实验数据表明高达 43.8%）是绝对物超所值的。
